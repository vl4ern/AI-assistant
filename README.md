# Ассистент студента

Персональный планировщик для студента БГУИР: личные задачи и дедлайны,
расписание группы с учебными неделями 1–4 и подгруппами, автоматический
план дня с учётом пар. У каждого пользователя — свои данные.

Этот README — главный документ проекта: как всё устроено, откуда какие
данные берутся, почему принято то или иное решение и как писать свои
модули, не ломая чужие.

## Быстрый старт

### Docker (рекомендуется)

```bash
cp .env.example .env
# впишите номер группы: IIS_GROUP_NUMBER=421701
make up
```

`make up` — одна команда для любого ПК: скачивает модели (если их ещё нет),
собирает backend и frontend, поднимает `api + web + postgres + llm` в
Docker. Первый запуск дольше обычного: нужно скачать ~3.4 ГБ моделей и
образ `llama.cpp`.

| Что                                 | Где                       |
| -------------------------------------- | ---------------------------- |
| Интерфейс                     | `http://localhost:5173`        |
| API-документация (Swagger) | http://localhost:8000/docs   |
| Проверка живости        | http://localhost:8000/health |
| llama-server (напрямую)    | http://localhost:8080/health |

Демо-аккаунт: **demo / demo** (с демо-задачами). Остальные пользователи
регистрируются сами — данные у каждого свои.

Если порт 8000 занят другим сервисом — поставьте свой в `.env`:
`API_PORT=8010`. Docker-compose подхватит автоматически. Аналогично
`LOCAL_LLM_PORT=8081`, если занят 8080 (внутри Docker API всё равно ходит
на `llm:8080`).

Останов: `make compose-down` или `docker compose down`. Стирание данных:
`docker compose down -v`.

### Шпаргалка по перезапуску (сохрани себе)

```bash
cd ~/projects/AI-assistant

# 1. Если Docker-демон не запущен (после перезагрузки с выключенным автостартом)
sudo systemctl start docker

# 2. Проверить .env (после `cp .env.example .env` всегда заново!)
#    API_PORT=8010, VITE_API_URL=http://localhost:8010, IIS_GROUP_NUMBER=421701
grep -E "API_PORT|IIS_GROUP" .env

# 3. Перезапустить проект целиком (модели скачаются при необходимости)
make up

# 4. Проверить, что всё живо
docker compose ps                       # api, web, postgres, llm — Up (llm — healthy)
curl --noproxy '*' http://localhost:8010/health   # {"status":"ok",...}
# интерфейс: http://localhost:5173

# Полезное:
docker compose logs api --tail 30       # логи backend
docker compose logs llm --tail 30       # логи локальной модели
make logs                               # api + llm в реальном времени
docker compose restart api             # перезапустить только API
docker compose down                    # остановить проект
```

Важно: в сети БГУИР трафик идёт через прокси — запросы к localhost из
терминала делайте с `--noproxy '*'`, иначе curl пойдёт через proxy.bsuir.by.
Сборка через медленный прокси может занимать до 10–15 минут — это нормально.

### Локально без Docker

```bash
make api-install   # venv + зависимости backend
make api-dev      # API на http://localhost:8000
make web-install  # зависимости frontend
make web-dev      # интерфейс на http://localhost:5173
make api-test     # тесты backend (99 шт.)
```

`.env` читают и Makefile, и backend (`app/core/settings.py` подключает
python-dotenv), переменные одни и те же.

### Распознавание задач из фото, текста и PDF

Кнопка «Добавить по фото или тексту» на странице «Задачи» работает через
локальную мультимодальную модель Qwen3.5 4B и `llama-server` из llama.cpp.

- **Вход**: текст, один файл (TXT/MD/CSV/JSON/PDF или JPG/PNG/WebP/GIF/BMP)
  или несколько файлов (лимит — `LOCAL_LLM_MAX_FILES`, по умолчанию 3) —
  до 3 штук, каждая со своим лимитом размера (`LOCAL_LLM_MAX_TEXT_KB`,
  `LOCAL_LLM_MAX_IMAGE_MB`).
- **PDF**: текст листов извлекается через `pypdf` (лимит страниц 50, лимит
  текста ~80 КБ). PDF без распознаваемого текста либо отклоняется, либо
  (для сканов) требует фотографию листа — скан не рендерится в этот MVP.
- **Несколько задач**: модель возвращает `{"tasks": [...]}` — массив из
  одной задачи или нескольких независимых задач (например, несколько
  лабораторных). Не дробление на подзадачи: элементы массива — самостоятельные
  задачи. Ответ может содержать до 3 задач (резерв токенов
  `LOCAL_LLM_MAX_TOKENS + 512`).

**Модели не хранятся в git.** Они весят ~3.4 ГБ, а GitHub не принимает
файлы больше 100 МБ; Git LFS на такой объём не влезает в бесплатную
квоту. Вместо этого `make models` скачивает те же файлы из публичного
репозитория `unsloth/Qwen3.5-4B-GGUF` на закреплённой ревизии и сверяет
SHA256 с `scripts/models.lock`. На всех компьютерах получаются одинаковые
модели. `make up` и `make llm-dev` вызывают `make models` автоматически.

Три режима запуска:

```bash
# 1. Всё в Docker (рекомендуется): api + web + postgres + llm
make up

# 2. Модель на хосте, backend локально
make llm-dev       # скачает модели и поднимет llama-server на :8080
make api-dev       # во втором терминале

# 3. API в Docker, модель на хосте
make llm-dev
LOCAL_LLM_BASE_URL=http://host.docker.internal:8080 \
  docker compose up -d --no-deps postgres api web
```

- В Docker API ходит на `http://llm:8080` (имя сервиса), порт 8080
  проброшен на хост для отладки и локального backend.
- Контейнер `llm` — официальный CPU-образ
  `ghcr.io/ggml-org/llama.cpp:server`, поэтому запуск одинаковый на
  Linux/Windows/macOS. Для NVIDIA используйте GPU-режим:
  `make up-gpu` (compose поверх `docker-compose.gpu.yml`: образ
  `ghcr.io/ggml-org/llama.cpp:server-cuda` + `gpus: all`, нужен
  NVIDIA Container Toolkit). GPU-слои модели/модельного проекта
  задаются через `LOCAL_LLM_GPU_LAYERS`.
- Локальный скрипт слушает `0.0.0.0`, чтобы был доступен из Docker; только
  с этой машины — `LOCAL_LLM_HOST=127.0.0.1 make llm-dev`. Если
  `llama-server` не в `PATH`:
  `LLAMA_SERVER_BIN=/path/to/llama-server make llm-dev`. На GPU с 4 ГБ
  начните с `LOCAL_LLM_GPU_LAYERS=0` (CPU) или небольшого числа слоёв.
- Если распознавание не нужно, поставьте `LOCAL_LLM_ENABLED=false` и
  поднимайте без контейнера модели:
  `docker compose up -d --no-deps postgres api web`.

### Стек

- **Backend**: Python 3.12, FastAPI, Pydantic v2, PostgreSQL 16
  (с in-memory фолбэком), SQLite для кэша интеграций.
- **Frontend**: React 19, TypeScript, Vite. Без UI-библиотек — один CSS-файл
  с переменными, тёмно-синяя тема.
- **Инфраструктура**: docker-compose (api + web + postgres + llm),
  официальный образ llama.cpp, GitHub Actions CI.

## Архитектура в двух словах

Четыре backend-модуля + фронтенд. Границы проведены по смыслу, а не
«кто что написал»:

```text
                        ┌──────────────────────────────┐
   внешний мир ────────►│  integrations                │
   (портал, файл, LLM)  │  кэш, недели, распознавание  │
                        └──────────────┬───────────────┘
                                       │ мост (kb_bridge)
                                       ▼
   HTTP-запросы ──► routes ──► ┌──────────────────────┐   ┌──────────┐
                               │ knowledge            │◄──│  auth    │
                               │ PostgreSQL / in-mem  │   │ токены   │
                               └──────────┬───────────┘   └──────────┘
                                          │ факты (задачи, события)
                                          ▼
                               ┌──────────────────────┐
                               │ intelligence         │
                               │ скоринг + план дня   │
                               └──────────┬───────────┘
                                          ▼
                               ┌──────────────────────┐
                               │ web (React)          │
                               │ расписание, задачи   │
                               └──────────────────────┘
```

**Три правила границ, нарушение которых уже однажды развалило проект:**

1. **Данными владеет только `knowledge`.** Никто не пишет в Postgres и не
   читает из него в обход `KnowledgeService`/репозитория. Иначе логика
   валидации и прав доступа расходится по копиям.
2. **Модули общаются через сервисный слой.** `intelligence` вызывает
   методы `KnowledgeRepository`; `integrations` кладёт факты через мост в
   `KnowledgeService`. Никаких `import` внутренностей чужого модуля.
3. **Внешний мир — только через `integrations`.** Ни один другой модуль
   не знает, как выглядит JSON портала БГУИР или Google Calendar.

Каждый сервис — обычный Python-класс, зависимости приходят через
конструктор. Вся сборка в одном месте — `container.py`. Для тестов это
означает: любой сервис можно собрать вручную с подделками.

В docker-compose `llama-server` — отдельный сервис `llm`; при локальном
запуске его поднимает `make llm-dev`. Для backend это всё равно внешний
источник, доступ к которому идёт только через `integrations`.

## Модули: как устроен каждый

### `knowledge` — хранилище фактов

Всё, что система «знает», хранится здесь: задачи, события, аккаунты.

```text
models.py                  Pydantic-модели: Task/TaskCreate, Event/EventCreate, User...
rules.py                   доменные правила (валидация дедлайнов, интервалов)
repository.py              абстрактный интерфейс хранилища (протокол)
in_memory_repository.py    реализация в памяти (фолбэк + тесты)
postgres_repository.py     реализация на PostgreSQL
schema.sql                 схема БД (создаётся при старте, идемпотентно)
migrations/0002_*.sql      миграции (накатываются при старте автоматически)
service.py                 KnowledgeService — правила + фасад над репозиторием
```

**Ключевые решения:**

- У задач и событий есть `user_id`. Значение `"shared"` — общие данные
  (например, расписание группы), их видят все; личные — только владелец.
  Фильтр `visible = (user_id == мой) or (user_id == "shared")` зашит в
  репозитории, чтобы ни один слой не смог его «забыть».
- Схема накатывается сама (`auto_init_schema`): сначала `schema.sql`
  (`CREATE TABLE IF NOT EXISTS...`), затем все файлы из `migrations/`
  по алфавиту — они тоже идемпотентны (`ADD COLUMN IF NOT EXISTS`).
- In-memory репозиторий — не заглушка «на потом», а рабочий режим: без
  PostgreSQL проект всё равно полностью функционален (данные до
  перезапуска). Это спасает демо и локальную разработку.

### `auth` — вход и личные данные

```text
models.py     RegisterRequest/LoginRequest/TokenResponse/User/UserPublic
service.py    AuthService: register / login / verify_token
```

- **Пароли**: PBKDF2-HMAC-SHA256, 200 000 итераций, случайная соль на
  пользователя. В базе только хеш + соль.
- **Токены**: самописный HMAC-подписанный JSON `{user_id, username, exp}`,
  живёт 7 дней. Проверка — пересчёт подписи (constant-time сравнение).
- **Кто это использует**: зависимость `get_current_user` (`api/deps.py`)
  достаёт токен из заголовка `Authorization: Bearer ...` и возвращает
  пользователя. Роуты задач/событий/плана обязаны её подключить — так
  изоляция данных enforcement'ится на уровне API, а не по честному слову.
- **Бесдействие**: фронт следит за активностью и через 30 минут молчания
  сам разлогинивает (токен остаётся валидным на сервере — защита от
  забытого окна, а не криптография).

Аккаунты хранятся в `users`-таблице репозитория knowledge — тот же
двойной бэкенд (Postgres/in-memory) работает и для них.

### `integrations` — внешние источники

Самый насыщенный модуль. Его внутренняя структура повторяет историю:
писался как отдельное приложение, затем был встроен внутрь backend'а.

```text
service.py              IntegrationService — фасад модуля
models/
  task.py               единая модель внешней задачи (dataclass)
  sync.py               SyncResult, ConflictNotification
  iis_models.py         парсер JSON портала + учебные недели
  google_models.py      модели Google Calendar
  extraction.py         TaskDraft / TaskDrafts — черновик(и) задачи (API-схема)
  __init__.py           API-схемы: Lesson, WeekInfo, IntegrationSyncResult
integration/
  interfaces.py         IServiceAdapter, ICacheStorage (абстракции)
  adapters/iis_adapter.py    портал БГУИР (+ общий парсер payload)
  adapters/google_calendar_adapter.py   Google Calendar (OAuth)
  adapters/llama_server_client.py       клиент OpenAI-совместимого llama-server
  task_extraction.py    промпт, проверка файлов (текст/PDF/картинки) и нормализация ответа LLM
  sync_scheduler.py     SyncScheduler: фоновая синхронизация + события
  cache_storage.py      SQLite-кэш по external_id
  conflict_resolver.py  слияние версий (LWW / merge-with-notify)
  retry_queue.py        повтор неуспешных синхронизаций
  kb_bridge.py          мост в базу знаний + дедупликация фактов
```

**Путь одного занятия от портала до интерфейса:**

```text
1. IisAdapter.fetch_changes()
   GET iis.bsuir.by/api/v1/schedule?studentGroup=421701
       ↓ tasks_from_iis_payload() — общий парсер (он же читает файлы)
2. IisScheduleItem.to_tasks()
   занятие + учебные недели → появления с конкретными датами
   (у каждого появления свой external_id с датой внутри)
       ↓
3. SyncScheduler._sync_adapter()
   SQLite-кэш: есть ли уже такой external_id?
   нет  → сохранить, событие "task_created"
   есть → ConflictResolver.resolve() (слияние версий)
       ↓
4. KnowledgeBaseBridge слушает события и пишет факты в KnowledgeService
   с дедупликацией по (источник, название, время начала)
       ↓
5. GET /v1/integrations/lessons поднимает занятия из кэша и парсит
   описание обратно в структуру (день, время, тип, аудитория, подгруппа)
       ↓
6. Фронтенд: расписание по неделям/подгруппам
```

**Распознавание задач из фото, текста и PDF** (кнопка на странице «Задачи»):
`POST /v1/tasks/extract` принимает текст и/или до 3 файлов
(TXT/MD/CSV/JSON/PDF, JPG/PNG/WebP/GIF/BMP). `TaskDraftExtractor`
проверяет формат (текст — UTF-8/CP1251, изображения и PDF — по сигнатурам),
извлекает текст из PDF через `pypdf`, отправляет запрос в `llama-server`
(в Docker — контейнер `llm`;
`/v1/chat/completions`, JSON-режим, «размышления» отключены) и нормализует
ответ: чинит приоритет, дедлайн, длительность и обрезает слишком длинные
поля. Наружу возвращается `TaskDrafts` с полем `tasks` — один черновик
(одна задача) или несколько (несколько независимых задач). Черновик(и)
**не** пишутся в базу знаний. Сохранение идёт обычным `POST /v1/tasks`
после подтверждения пользователем, поэтому правило «данными владеет
`knowledge`» не нарушается, а внешний мир (локальная модель) остаётся
внутри `integrations`.

**Фоновая синхронизация** стартует вместе с приложением (lifespan в
`main.py`) и опрашивает IIS раз в 2 часа. `RetryQueue` возвращает
повторные попытки при сбоях.

**Импорт из файла** (`POST /v1/integrations/import-file`) принимает XLSX
с расписанием группы. Парсер (`xlsx_import.py`) превращает лист в формат
портала и прогоняет через **тот же конвейер** (одноразовый адаптер → кэш →
мост → база знаний). Поэтому файл и онлайн-синхронизация не могут
разойтись в результатах. Номер группы берётся из файла (или из поля
ввода), импортированное расписание **полностью заменяет** прежнее и
становится текущим — смешивания расписаний двух групп не происходит.

### `intelligence` — планировщик и скоринг

```text
scheduler.py      GreedyScheduler — жадное заполнение свободных окон
ml_scoring.py     MLScoringService — линейная регрессия «важности» задач
service.py        SchedulerService — оркестратор (rebuild/today/feedback)
models.py         SchedulePlan, ScheduledSlot, TodayView, ReorderFeedback
utils/time_utils.py  рабочие окна бодрствования
```

**Как строится план** (`POST /v1/schedule/rebuild`, `service.py:rebuild`):

1. Берём факты: активные задачи + события (и личные, и общие пары).
2. Сбрасываем старые интервалы у подвижных задач.
3. `MLScoringService.build_score_map()` — скор всех задач.
4. `GreedyScheduler.build_plan()` — по убыванию скора раскладывает задачи
   в свободные окна: сутки минус события минус нерабочие часы
   (`WAKE_START_HOUR..WAKE_END_HOUR`), шаг слота `SCHEDULE_SLOT_MINUTES`.
   Учитывает зависимости (`depends_on`) и разбиение длинных задач
   (`allow_split`, `min_chunk_minutes`).
5. Интервалы сохраняются в задачах, флаг «расписание грязное» снимается.

**Скоринг** — SGD-регрессия поверх трёх признаков:
`[свободные минуты до дедлайна / 1440, приоритет / 4, оценка минут / 240]`.
Признаки нормализованы — без этого SGD расходился и выдавал скор −10¹⁹
(было, починено). Модель сразу готова к работе: при старте обучается на
216 синтетических примерах («здравый смысл»: чем ближе дедлайн и выше
приоритет — тем важнее). Дальше **дообучается на действиях пользователя**:
перетащил задачу выше соседней — пример «её скор должен быть между
соседями»; завершил просроченную — бонус. Примеры копятся пакетами
(`ML_RETRAIN_BATCH_SIZE`) и вливаются через `partial_fit`. Предсказание
зажато в [0, 200].

Фидбек-цикл: `POST /v1/schedule/reorder-feedback` — запись «ручного»
порядка задач как обучающего примера.

### `web` — интерфейс

Один `App.tsx` (вход + 5 страниц: Обзор, Задачи, Расписание, План,
История) и один `index.css` с темой на CSS-переменных.


## Учебные недели и подгруппы

**Недели.** Расписание БГУИР циклично: учебная неделя 1 — один набор
пар, неделя 2 — другой, всего 4 варианта. Текущая неделя вычисляется от
даты начала семестра:

```python
academic_week(day, semester_start) = (day - semester_start).days // 7 % 4 + 1
```

При синхронизации каждое занятие разворачивается в **появления**:
перебираются дни горизонта (`IIS_HORIZON_DAYS`, по умолчанию 28 — полный
цикл), и для каждого совпадающего дня недели, чья учебная неделя входит
в `weekNumber` занятия, создаётся появление с конкретной датой.
У появления свой `external_id` (внутри хеша — дата), поэтому недели не
склеиваются в кэше.

**Зачем это планировщику:** появление попадает в базу знаний как событие
на свою дату — планер видит реальные занятые интервалы и не ставит задачу
на время чужой пары.

**Подгруппы.** У занятия есть `numSubgroup`: 0 — общая пара, 1/2 — только
для подгруппы. Одно и то же время может быть двумя разными предметами
(1-я подгруппа на ИГИСиТ, 2-я на СтатОИВ), а один предмет может менять
подгруппы по неделям. В интерфейсе: бейдж «1 подгр.» / «2 подгр.» и
фильтр «Все / Общие / 1 подгруппа / 2 подгруппа». В кэше подгруппа входит
в `external_id`, поэтому такие пары не склеиваются.

## Как добавить свой модуль

Модуль — это папка `apps/api/app/modules/<имя>` + сервисный класс +
регистрация в `container.py` + свои роуты. Пошагово:

**1. Структура**

```text
modules/<имя>/
  __init__.py
  models.py      # pydantic-схемы запросов/ответов
  service.py    # вся логика; зависимости — через __init__
```

**2. Сервис — обычный класс, без глобального состояния**

```python
# modules/<имя>/service.py
from app.modules.knowledge.repository import KnowledgeRepository

class MyService:
    def __init__(self, repository: KnowledgeRepository, ...) -> None:
        self._repository = repository   # только сервисный слой чужих модулей

    def do_stuff(self, user_id: str) -> MyResult: ...
```

**3. Регистрация в `container.py`** — единственное место сборки:

```python
self.my_service = MyService(repository=self.knowledge_repository)
```

**4. Роуты** — `app/api/routes_<имя>.py`, подключить в `api/router.py`.
Если эндпоинт отдаёт личные данные:

```python
from app.api.deps import get_current_user

@router.get("/things")
def list_things(user: UserPublic = Depends(get_current_user)):
    return container.my_service.list_things(user.id)   # фильтр по владельцу!
```

**5. Данные.** Нужны новые сущности? Схема — в `knowledge/schema.sql`
(+ идемпотентная миграция в `knowledge/migrations/000N_*.sql`), модель —
в `knowledge/models.py`, методы — в `repository.py` и обеих реализациях.
**Не подключайтесь к базе из своего модуля напрямую.**

**6. Тесты** — `apps/api/tests/<имя>/`. Сервисы собираются руками с
`InMemoryKnowledgeRepository` и подделками — база не нужна:

```python
def test_my_service():
    service = MyService(repository=InMemoryKnowledgeRepository())
    assert service.do_stuff(user_id="u1") == ...
```

**7. Фронтенд** — `src/api/<имя>.ts` (типизированный клиент) + страница
или секция в `App.tsx`.

**Чеклист перед PR:**

- [ ] модуль не импортирует внутренности других модулей (только service/repository-слой)
- [ ] не ходит в базу в обход `knowledge`
- [ ] личные эндпоинты требуют `get_current_user` и фильтруют по `user.id`
- [ ] тесты есть и проходят: `make api-test`
- [ ] тесты не зависят от времени суток (фиксируйте даты/часы бодрствования, а не `now + N часов`)
- [ ] фронт собирается: `npm run build && npm run lint` в `apps/web/frontend`
- [ ] если менялся API — обновлён `packages/contracts/openapi.yaml`

| `LOCAL_LLM_CTX_SIZE`                             | размер контекста                                                                    | `16384`                                                                    |
| `LOCAL_LLM_IMAGE_MIN_TOKENS`                     | минимум токенов на изображение (Qwen-VL)                      | `1024`                                                                     |

## Почему так, а не иначе

Короткие записи о принятых решениях (ADR-lite). При изменении решения —
допишите сюда новое и почему.

- **Почему факты хранит один модуль.** В первой версии проекта каждый
  модуль держал свои данные сам — итог: три несовместимые модели «задачи»
  и ничего не работало вместе. Теперь `knowledge` — единственный владелец
  данных с правилами и изоляцией, остальные — потребители.
- **Почему in-memory фолбэк.** Демо и локальная разработка без Postgres
  должны работать целиком. Фолбэк включается автоматически, если база
  недоступна (в т.ч. из-за занятого порта на машине разработчика).
- **Почему кэш интеграций — SQLite, а не Postgres.** Это кэш сырых
  внешних данных с семантикой `external_id` (дедупликация источника), а
  не факты. Переживает перезапуски, не требует схемы, не засоряет базу
  знаний. Мост перекладывает из него в базу только нужное.
- **Почему токены, а не серверные сессии.** Stateless: не нужно хранить
  сессии, любое количество инстансов API работает одинаково. HMAC-подпись
  на stdlib — без лишних зависимостей. 7 дней жизни + клиентский
  авто-выход по бездействию.
- **Почему занятия разворачиваются в появления с датами.** Планировщику
  нужны конкретные занятые интервалы. «Ближайший вторник» ломает план и
  порождает клоны в неделях. Дата в `external_id` — появления разных
  недель не склеиваются.
- **Почему фильтрация недель на фронтенде.** Сервер честно отдаёт все
  появления с их неделей; «как сворачивать» (физическая неделя vs
  шаблон) — вопрос отображения, а не данных.
- **Почему дедупликация фактов по (источник, название, начало).** У базы
  знаний нет внешних ключей источников; эта тройка однозначно
  идентифицирует занятие в событиях. Защищает от дублей при пересинках
  и пересозданиях кэша.
- **Почему импорт файла через тот же конвейер.** Отдельный код импорта
  гарантированно разошёлся бы с онлайн-синхронизацией. Один парсер
  (`tasks_from_iis_payload`) — одинаковая семантика из любого источника.
- **Почему распознавание задачи живёт в `integrations`.** Локальная LLM —
  такой же внешний источник, как портал или Google: остальной backend не
  должен знать деталей его API. Модуль отдаёт только черновики
  `TaskDrafts` (массив `tasks`), а сохранение остаётся за `knowledge`. Модель
  можно выключить (`LOCAL_LLM_ENABLED=false`), и остальные сценарии
  продолжат работать.
- **Почему модели не в git, а скачиваются.** GGUF-файлы весят 3.4 ГБ;
  GitHub отклоняет файлы больше 100 МБ, а бесплатный Git LFS (1 ГБ) их не
  вмещает. Поэтому в git лежат только `scripts/models.lock` с ревизией
  Hugging Face и SHA256, а `make models` скачивает те же файлы на любом ПК.
  Это воспроизводимее, чем «у меня модель есть, а у тебя нет», и не
  раздувает историю репозитория.

## Дневник работы

Живой журнал ключевых решений. Новые записи — сверху.

### 04.11.2026 — задачи из нескольких файлов и несколько задач через локальную LLM

- **Несколько задач**: `POST /v1/tasks/extract` теперь возвращает
  `TaskDrafts { "tasks": [...] }`. Модель сама решает, из материала одна
  задача или несколько независимых задач (например, несколько лабораторных
  из одного текста) — промпт требует массив `tasks`, не дробит задачи на
  подзадачи.
- **Несколько файлов**: multipart-параметр `file` принимает массив
  бинаров (до 3 — `LOCAL_LLM_MAX_FILES`; лимит размера на файл — прежние
  `LOCAL_LLM_MAX_TEXT_KB` / `LOCAL_LLM_MAX_IMAGE_MB`). Текстовые файлы
  складываются в один промпт с указанием названий; картинки — отдельные
  image-parts в одном запросе.
- **PDF**: текст листов извлекается через `pypdf` (лимит страниц 50, лимит
  текста ~80 КБ). Без извлекаемого текста — понятное сообщение.
- **Фронт**: модалка «Распознать задачу» умеет несколько файлов
  (input `multiple`) и работает с очередью черновиков: создание задачи из
  очереди → следующая предлагается автоматически; «Далее» / «Пропустить» для
  обхода; «Исправить в форме» → ручная форма.
- Тесты: мультизадачные ответы, несколько файлов/картинок в промпт,
  PDF, лимит файлов (107 тестов в `apps/api/tests`).

### 03.11.2026 — Docker-запуск llama-server и автозагрузка моделей

- `llm` — отдельный сервис в docker-compose на официальном CPU-образе
  `ghcr.io/ggml-org/llama.cpp:server`; API ходит на `http://llm:8080`.
  Весь проект поднимается одинаково на любом ПК: `make up`.
- Модели не коммитятся: они весят 3.4 ГБ, а GitHub не принимает файлы
  больше 100 МБ (бесплатный Git LFS тоже меньше). `make models` скачивает
  `Qwen3.5-4B-UD-Q4_K_XL.gguf` и `mmproj-F16.gguf` из закреплённой ревизии
  `unsloth/Qwen3.5-4B-GGUF` и сверяет SHA256 по `scripts/models.lock`.
  `make up` и `make llm-dev` вызывают загрузку автоматически.
- Локальный запуск без Docker остался: `make llm-dev` (нужен собранный
  `llama-server` в `PATH`).

### 03.11.2026 — задачи из фото и текста (локальная Qwen3.5 4B)

- На странице «Задачи» появилась кнопка «Добавить по фото или тексту»:
  пользователь вставляет текст или выбирает текстовый файл/изображение,
  локальная модель возвращает черновик, форму можно сразу отправить

- Добавлены тесты извлечения, клиента llama-server и контракта; всего
  99 тестов.

### 26.10.2026 — календарь месяца и расписание по группе пользователя

- **Страница «Календарь»**: месяц плашками (как просили — обычный вид
  календаря). В левом углу каждой плашки — контрастный бейдж учебной
  недели («1 нед.»), внутри — краткая сводка (сколько пар, задач,
  дедлайнов, первым предметом). Клик по плашке раскрывает день:
  крупное число, день недели, месяц, и три подписанных блока —
  «Расписание университета», «Личные задачи», «Дедлайны».
- **Группа вводится пользователем**: на странице расписания поле
  «Номер группы» + кнопка «Загрузить группу» (`POST /v1/integrations/sync-group`).
  Группа из настроек — теперь лишь значение по умолчанию; введённая
  группа запоминается и для фоновых синхронизаций, данные прошлой
  группы вычищаются реконсиляцией.
- **Исправлено накопление записей в воскресенье**: всё без дня недели
  (экзамены, консультации, кривые импорты) сваливалось в колонку

  отдельная секция «Экзамены и события по датам», отсортированная

### 08.10.2026 — гигиена кэша расписания

После месяца эксплуатации выяснилось: кэш появлений копит прошлое и «сирот».
В недельном виде каждая пара показывалась дважды (прошедший цикл + будущий),
а консультации портала светились как «Без названия». Исправлено тремя
механизмами в `integrations`:

- **уборка**: после каждой синхронизации из кэша удаляются появления
  с прошедшими датами (кэш держит только текущий горизонт);
- **реконсиляция**: портал иногда правит записи — меняется `external_id`,
  и старая копия зависает в кэше. Теперь после синхронизации IIS будущие
  появления, которых не было в ответе портала, удаляются, а при чтении
  дубликаты сворачиваются по естественному ключу (дата, время, предмет,
  аудитория, подгруппа);
- **названия анонсов**: у записей без предмета (консультации) названием
  становится примечание портала, а не «Без названия».

Заодно два старых теста недель переписаны с фиксированной датой генерации
(захардкоденные даты «постарели» — тесты зависели от дня запуска).
Итог: 71 тест, во всех неделях расписания ноль клонов.

### 08.10.2026 — визуальный апгрейд интерфейса

Тема переработана до «премиального» тёмно-синего: слоистые градиенты фона,
свечение активных элементов, мягкие тени карточек, плавные переходы
и микро-анимации (появление страниц, подъём кнопок), стилизованный

Появления из разных физических недель склеивались в одном дне: фильтр шёл

### 28.10.2026 — расписание одной группы, XLSX-импорт, настройки интерфейса

- Расписание показывается только для текущей группы (последний ввод
  номера или импорт файла): группа помечается у каждой записи, `GET /v1/integrations/current-group` отдаёт её фронту, под заголовком
  «Расписание» подписана группа. Импорт полностью заменяет прежнее

- Импорт из файла переведён с JSON на XLSX: `POST /v1/integrations/import-file` (multipart), парсер `xlsx_import.py`
  понимает табличный макет и «день недели заголовком», группу берёт

- Из ветки коллеги `integration_module2` взяты удавшиеся решения:
  HTTP-сессия с retry/backoff в Iis-адаптере и полевой
  конфликт-резолвер (свежая сторона выигрывает по конфликтующим
  полям, неконфликтующие добираются из второй).
- Затычка настроек интерфейса (модуль планирования развивается):
  шестерёнка в шапке с лёгкой анимацией прокрутки — тема (тёмная /
  светлая: белые и синие цвета), язык (ru/en) и размер шрифта.
  Настройки хранятся в localStorage.

Корневая проблема проекта: модуль интеграции писался как отдельное

рабочих веток собраны в `main`.
