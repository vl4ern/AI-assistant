# База знаний интеллектуального ассистента планирования

## 1. Назначение базы знаний

База знаний проекта предназначена для хранения и структурирования сведений, необходимых интеллектуальному ассистенту планирования учебной нагрузки, дедлайнов и личных задач.

В рамках 4 семестра основной результат проекта рассматривается не как полноценный решатель задач и не как завершённая интеллектуальная система, а как минимально жизнеспособная версия базы знаний и средств обращения к ней.

База знаний должна обеспечивать:

- хранение фактов о задачах пользователя;
- хранение фактов о событиях и занятых временных интервалах;
- хранение отношений зависимости между задачами;
- проверку базовых ограничений целостности данных;
- предоставление структурированных данных для последующего развития решателя задач и пользовательского интерфейса.

## 2. Предметная область

Предметная область проекта — персональное и учебное планирование.

В этой области пользователь работает с учебными задачами, личными делами, дедлайнами, событиями календаря и временными ограничениями. База знаний фиксирует не только сами задачи, но и свойства, влияющие на дальнейшее планирование: длительность, приоритет, срок выполнения, статус и зависимости.

Основные объекты предметной области:

- задача;
- событие;
- зависимость между задачами;
- дедлайн;
- приоритет;
- статус выполнения;
- временной интервал.

## 3. Формализм представления знаний

В проекте используется структурированное представление знаний на основе реляционной модели данных и объектных моделей backend-приложения.

На уровне программной реализации знания представлены:

- Pydantic-моделями в backend;
- таблицами PostgreSQL;
- связями между таблицами;
- ограничениями целостности;
- правилами предметной области, реализуемыми на уровне сервиса и репозитория.

Такой формализм выбран по следующим причинам:

- он подходит для хранения структурированных фактов о задачах, событиях и зависимостях;
- он обеспечивает проверку типов и ограничений на уровне модели и базы данных;
- он позволяет выполнять поиск, фильтрацию и дальнейшую обработку знаний;
- он пригоден для последующего подключения решателя задач, планировщика и внешних интеграций.

## 4. Декларативные знания

Декларативные знания описывают факты предметной области: какие объекты существуют, какими свойствами они обладают и какие отношения между ними установлены.

### 4.1 Task

Сущность `Task` описывает задачу пользователя.

Основные атрибуты:

| Атрибут | Назначение |
|---|---|
| `id` | уникальный идентификатор задачи |
| `title` | краткое название задачи |
| `description` | дополнительное описание |
| `estimated_minutes` | ожидаемая длительность выполнения |
| `priority` | приоритет задачи |
| `deadline` | срок выполнения |
| `workspace_id` | рабочая область, например `study` |
| `project_id` | проект или учебная дисциплина |
| `status` | состояние задачи |
| `depends_on` | список задач, от которых зависит текущая задача |
| `scheduled_start` | запланированное время начала |
| `scheduled_end` | запланированное время окончания |

Смысл сущности: задача является основным фактом базы знаний, вокруг которого строится планирование.

### 4.2 Event

Сущность `Event` описывает событие, занимающее временной интервал.

Основные атрибуты:

| Атрибут | Назначение |
|---|---|
| `id` | уникальный идентификатор события |
| `title` | название события |
| `start_at` | время начала события |
| `end_at` | время окончания события |
| `source` | источник события: ручной ввод, расписание, календарь и т.п. |

Смысл сущности: событие фиксирует занятость пользователя и может использоваться как временное ограничение для будущего планирования.

### 4.3 TaskDependency

Сущность `TaskDependency` описывает отношение зависимости между задачами.

Основные атрибуты:

| Атрибут | Назначение |
|---|---|
| `task_id` | задача, которая имеет зависимость |
| `depends_on_task_id` | задача, от которой зависит текущая |

Смысл сущности: если задача A зависит от задачи B, то задача A не должна рассматриваться как полностью независимая от B.

## 5. Отношения между сущностями

В базе знаний используются следующие отношения:

| Отношение | Описание | Пример |
|---|---|---|
| `Task has Deadline` | задача имеет срок выполнения | лабораторная должна быть выполнена до пятницы |
| `Task has Priority` | задача имеет уровень важности | подготовка к экзамену имеет высокий приоритет |
| `Task has Status` | задача находится в определённом состоянии | задача выполнена или ожидает выполнения |
| `Task depends_on Task` | одна задача зависит от другой | отчёт зависит от завершения эксперимента |
| `Event occupies TimeInterval` | событие занимает интервал времени | лекция занимает время с 10:00 до 11:35 |
| `Event has Source` | событие имеет источник происхождения | событие получено из расписания университета |

Эти отношения позволяют представить базу знаний не как набор разрозненных записей, а как связанную структуру сведений о планировании.

## 6. Процедурные знания и правила

Процедурные знания представлены правилами, которые определяют допустимость и смысл обработки фактов.

### R1. Ограничение длительности задачи

Задача должна иметь положительную длительность. В проекте длительность ограничена диапазоном от 15 до 1440 минут.

Назначение правила: исключить некорректные задачи с нулевой, отрицательной или чрезмерной длительностью.

### R2. Ограничение приоритета

Приоритет задачи должен находиться в допустимом диапазоне от 1 до 4.

Назначение правила: обеспечить единообразное сравнение задач по важности.

### R3. Ограничение статуса

Статус задачи должен принадлежать фиксированному множеству:

- `todo`;
- `in_progress`;
- `completed`;
- `cancelled`;
- `blocked`.

Назначение правила: исключить неформализованные состояния задачи.

### R4. Ограничение зависимости

Задача не может зависеть сама от себя.

Назначение правила: исключить очевидное логическое противоречие в базе знаний.

### R5. Событие как занятый временной интервал

Каждое событие задаёт интервал занятости пользователя через `start_at` и `end_at`.

Назначение правила: сохранить знания о времени, которое не должно рассматриваться как свободное при последующем планировании.

### R6. Источник события

Каждое событие имеет поле `source`, которое показывает происхождение факта.

Назначение правила: отличать события, введённые вручную, от событий, полученных из внешних источников, например расписания университета или календаря.

## 7. Ограничения целостности

Для обеспечения согласованности базы знаний используются ограничения:

- уникальность идентификаторов задач и событий;
- обязательность названия задачи и события;
- ограничение длительности задачи;
- ограничение диапазона приоритета;
- ограничение допустимых статусов задачи;
- ссылочная целостность зависимостей между задачами;
- запрет зависимости задачи от самой себя;
- индексация часто используемых полей: статус задачи, дедлайн, время начала события.

Эти ограничения позволяют поддерживать непротиворечивость базы знаний и предотвращать сохранение некорректных фактов.

## 8. Сценарии обращения к базе знаний

### Сценарий 1. Создание задачи

Пользователь создаёт задачу через веб-интерфейс. Frontend отправляет запрос в backend, backend проверяет данные и сохраняет задачу в PostgreSQL.

Результат: в базе знаний появляется новый факт типа `Task`.

### Сценарий 2. Получение списка задач

Пользователь открывает сайт или обновляет страницу. Frontend запрашивает список задач у backend. Backend получает задачи из PostgreSQL и возвращает их пользователю.

Результат: пользователь видит актуальное состояние базы знаний.

### Сценарий 3. Сохранение знаний после перезапуска

После остановки и повторного запуска Docker-контейнеров созданные задачи остаются в PostgreSQL.

Результат: знания сохраняются долговременно, а не только в памяти приложения.

### Сценарий 4. Хранение событий

Система может хранить события, занимающие временные интервалы. Такие события могут быть введены вручную или получены из внешних источников.

Результат: база знаний содержит информацию о занятости пользователя.

### Сценарий 5. Хранение зависимостей

Если одна задача зависит от другой, это отношение сохраняется в таблице `task_dependencies`.

Результат: база знаний фиксирует не только отдельные задачи, но и связи между ними.

## 9. Границы применимости

Текущая версия базы знаний предназначена для хранения и базового использования сведений о задачах, событиях и зависимостях.

Она применима для:

- учебного планирования;
- хранения дедлайнов;
- хранения событий расписания;
- фиксации зависимостей между задачами;
- демонстрации работы MVP базы знаний.

Текущая версия не является полноценным решателем задач. Сложное автоматическое планирование, оптимизация расписания и интеллектуальные рекомендации относятся к следующим этапам развития проекта.

## 10. Перспективы развития

На следующих этапах база знаний может быть расширена:

- интеграцией с Google Calendar и расписанием университета;
- добавлением новых типов фактов;
- добавлением более сложных правил вывода;
- использованием решателя задач для автоматического планирования;
- построением объяснений, почему задача была запланирована в конкретное время.

Таким образом, текущий модуль базы знаний создаёт основу для дальнейшего развития интеллектуального ассистента в последующих семестрах.
