# Схема базы данных модуля базы знаний

## 1. Назначение схемы

Схема базы данных описывает физическое хранение базы знаний интеллектуального ассистента планирования.

В рамках проекта PostgreSQL используется не просто как хранилище записей, а как основа базы знаний, где фиксируются:

- факты о задачах пользователя;
- факты о событиях и занятых временных интервалах;
- отношения зависимости между задачами;
- ограничения целостности, поддерживающие непротиворечивость знаний.

Физическая схема базы данных реализована в файле:

```text
apps/api/app/modules/knowledge/schema.sql
```

## 2. Общая структура базы знаний

База знаний состоит из трёх основных таблиц:

```text
tasks
events
task_dependencies
```

Их смысл:

| Таблица | Назначение |
|---|---|
| `tasks` | хранение фактов о задачах пользователя |
| `events` | хранение фактов о событиях и занятых временных интервалах |
| `task_dependencies` | хранение отношений зависимости между задачами |

Общая логическая схема:

```text
Task
 ├── has deadline
 ├── has priority
 ├── has status
 ├── may have scheduled_start / scheduled_end
 └── may depend on another Task

Event
 ├── has start_at
 ├── has end_at
 └── has source

TaskDependency
 ├── task_id
 └── depends_on_task_id
```

## 3. Таблица `tasks`

Таблица `tasks` хранит основные факты о задачах пользователя.

### 3.1 Назначение

Каждая запись в таблице `tasks` представляет одну задачу, которую пользователь планирует выполнить.

Примеры задач:

- выполнить лабораторную работу;
- подготовиться к тесту;
- написать раздел пояснительной записки;
- отправить отчёт;
- повторить материал к экзамену.

### 3.2 Поля таблицы

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `TEXT` | уникальный идентификатор задачи |
| `title` | `VARCHAR(200)` | название задачи |
| `description` | `TEXT` | подробное описание задачи |
| `estimated_minutes` | `INTEGER` | ожидаемая длительность выполнения в минутах |
| `priority` | `INTEGER` | приоритет задачи |
| `deadline` | `TIMESTAMPTZ` | срок выполнения задачи |
| `workspace_id` | `TEXT` | рабочая область пользователя |
| `project_id` | `TEXT` | проект, дисциплина или категория |
| `auto_reschedule` | `BOOLEAN` | возможность автоматического перепланирования |
| `allow_split` | `BOOLEAN` | возможность разделения задачи на части |
| `min_chunk_minutes` | `INTEGER` | минимальная длительность части задачи |
| `status` | `TEXT` | статус выполнения задачи |
| `created_at` | `TIMESTAMPTZ` | время создания задачи |
| `updated_at` | `TIMESTAMPTZ` | время последнего обновления |
| `scheduled_start` | `TIMESTAMPTZ` | запланированное время начала |
| `scheduled_end` | `TIMESTAMPTZ` | запланированное время окончания |

### 3.3 Ограничения таблицы

В таблице `tasks` используются следующие ограничения:

```sql
id TEXT PRIMARY KEY
```

Идентификатор задачи должен быть уникальным.

```sql
title VARCHAR(200) NOT NULL
```

Название задачи обязательно.

```sql
estimated_minutes INTEGER NOT NULL CHECK (estimated_minutes >= 15 AND estimated_minutes <= 1440)
```

Длительность задачи должна быть от 15 минут до 24 часов.

```sql
priority INTEGER NOT NULL CHECK (priority >= 1 AND priority <= 4)
```

Приоритет задачи должен находиться в диапазоне от 1 до 4.

```sql
status TEXT NOT NULL CHECK (status IN ('todo', 'in_progress', 'completed', 'cancelled', 'blocked'))
```

Статус задачи должен принадлежать заранее определённому множеству допустимых состояний.

### 3.4 Значение для базы знаний

Таблица `tasks` хранит декларативные знания о задачах:

- что нужно сделать;
- сколько времени это займёт;
- насколько задача важна;
- когда её нужно завершить;
- в каком состоянии она находится;
- может ли она быть перепланирована;
- может ли она быть разбита на части.

Эти данные могут использоваться будущим решателем задач для построения расписания и объяснения решений.

## 4. Таблица `events`

Таблица `events` хранит факты о событиях, которые занимают временные интервалы.

### 4.1 Назначение

События описывают занятость пользователя.

Примеры событий:

- лекция;
- практическое занятие;
- консультация;
- встреча;
- событие из календаря;
- занятие из расписания университета.

### 4.2 Поля таблицы

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `TEXT` | уникальный идентификатор события |
| `title` | `VARCHAR(200)` | название события |
| `start_at` | `TIMESTAMPTZ` | время начала события |
| `end_at` | `TIMESTAMPTZ` | время окончания события |
| `source` | `TEXT` | источник события |

### 4.3 Ограничения таблицы

```sql
id TEXT PRIMARY KEY
```

Идентификатор события должен быть уникальным.

```sql
title VARCHAR(200) NOT NULL
```

Название события обязательно.

```sql
start_at TIMESTAMPTZ NOT NULL
end_at TIMESTAMPTZ NOT NULL
```

У события обязательно должны быть время начала и время окончания.

```sql
source TEXT NOT NULL DEFAULT 'manual'
```

Каждое событие должно иметь источник. Если источник не указан явно, используется значение `manual`.

### 4.4 Значение для базы знаний

Таблица `events` хранит знания о занятых временных интервалах.

События важны, потому что они задают временные ограничения. Например, если у пользователя есть лекция с 10:00 до 11:35, то будущий планировщик не должен ставить задачу на это время.

Поле `source` позволяет отличать события по происхождению:

| Source | Значение |
|---|---|
| `manual` | событие введено вручную |
| `bsuir-lms` | событие связано с учебным расписанием |
| `google-calendar` | событие может быть получено из Google Calendar |
| `mock` | тестовый источник данных |

## 5. Таблица `task_dependencies`

Таблица `task_dependencies` хранит отношения зависимости между задачами.

### 5.1 Назначение

Некоторые задачи не являются независимыми. Например:

- нельзя оформить отчёт, пока не выполнена лабораторная работа;
- нельзя подготовить презентацию, пока не готов основной материал;
- нельзя отправить проект, пока не завершено тестирование.

Такие отношения фиксируются в таблице `task_dependencies`.

### 5.2 Поля таблицы

| Поле | Тип | Назначение |
|---|---|---|
| `task_id` | `TEXT` | задача, которая имеет зависимость |
| `depends_on_task_id` | `TEXT` | задача, от которой зависит текущая |

### 5.3 Ограничения таблицы

```sql
task_id TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE
```

Зависимая задача должна существовать в таблице `tasks`.

```sql
depends_on_task_id TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE
```

Задача, от которой зависит текущая, также должна существовать в таблице `tasks`.

```sql
PRIMARY KEY (task_id, depends_on_task_id)
```

Одна и та же зависимость не должна дублироваться.

```sql
CHECK (task_id <> depends_on_task_id)
```

Задача не может зависеть сама от себя.

### 5.4 Значение для базы знаний

Таблица `task_dependencies` хранит не отдельные факты, а отношения между фактами.

Это позволяет базе знаний описывать структуру задач, а не только их список.

Например:

```text
Task A: Написать пояснительную записку
Task B: Собрать материалы и скриншоты

Task A depends_on Task B
```

Смысл: задача A не должна рассматриваться как полностью готовая к выполнению без выполнения задачи B.

## 6. Индексы

В схеме используются индексы:

```sql
CREATE INDEX IF NOT EXISTS idx_tasks_status ON tasks(status);
CREATE INDEX IF NOT EXISTS idx_tasks_deadline ON tasks(deadline);
CREATE INDEX IF NOT EXISTS idx_events_start_at ON events(start_at);
```

Их назначение:

| Индекс | Назначение |
|---|---|
| `idx_tasks_status` | ускоряет поиск задач по статусу |
| `idx_tasks_deadline` | ускоряет поиск задач по дедлайну |
| `idx_events_start_at` | ускоряет поиск событий по времени начала |

Индексы важны для дальнейшего развития системы, потому что будущий планировщик будет часто обращаться к задачам по статусам, срокам и временным ограничениям.

## 7. Связь схемы с объектными моделями backend

Физическая схема базы данных связана с Pydantic-моделями backend.

Основные соответствия:

| Pydantic-модель | Таблица PostgreSQL |
|---|---|
| `Task` | `tasks` |
| `TaskCreate` | используется при создании записи в `tasks` |
| `Event` | `events` |
| `EventCreate` | используется при создании записи в `events` |
| `depends_on` внутри `Task` | `task_dependencies` |

Это обеспечивает единое представление знаний на уровне API, backend-логики и базы данных.

## 8. Проверка работоспособности схемы

После запуска проекта можно проверить наличие таблиц командой:

```bash
docker compose exec postgres psql -U assistant -d assistant_db
```

Внутри PostgreSQL:

```sql
\dt
```

Ожидаемый результат:

```text
events
task_dependencies
tasks
```

Проверка задач:

```sql
SELECT id, title FROM tasks;
```

Проверка событий:

```sql
SELECT id, title, start_at, end_at, source FROM events;
```

Проверка зависимостей:

```sql
SELECT task_id, depends_on_task_id FROM task_dependencies;
```

## 9. Роль схемы в курсовом проекте 4 семестра

Для 4 семестра эта схема является основой базы знаний.

Она показывает:

- какие факты хранит система;
- какие отношения существуют между фактами;
- какие ограничения защищают базу знаний от противоречий;
- какие данные могут использоваться в последующих семестрах для решателя задач и интерфейса интеллектуальной системы.

Таким образом, PostgreSQL-схема является не только технической базой данных, но и формальной структурой хранения знаний интеллектуального ассистента.
