# Тестирование базы знаний

## 1. Назначение тестирования

Тестирование проводится для проверки корректности работы базы знаний интеллектуального ассистента планирования.

Основная цель тестирования — убедиться, что система:

- корректно запускается через Docker;
- использует PostgreSQL как долговременное хранилище знаний;
- сохраняет задачи после обновления страницы и перезапуска контейнеров;
- применяет правила базы знаний при создании задач и событий;
- отклоняет некорректные факты, нарушающие правила предметной области.

## 2. Проверка запуска проекта

Проект запускается командой:

```bash
docker compose up -d --build
```

После запуска состояние контейнеров проверяется командой:

```bash
docker compose ps
```

Ожидаемый результат:

```text
api        Up
web        Up
postgres   Up
```

Это означает, что запущены основные части системы:

- frontend;
- backend;
- PostgreSQL.

## 3. Проверка backend

Логи backend проверяются командой:

```bash
docker compose logs --tail=50 api
```

Ожидаемый результат:

```text
Application startup complete
```

Также backend можно проверить через health-check:

```text
http://localhost:8000/health
```

И через Swagger:

```text
http://localhost:8000/docs
```

## 4. Проверка подключения к PostgreSQL

Проверка доступности PostgreSQL:

```bash
docker compose exec postgres pg_isready -U assistant -d assistant_db
```

Ожидаемый результат:

```text
accepting connections
```

Проверка того, что backend использует PostgreSQL:

```bash
docker compose exec api python -c "from app.container import container; print(type(container.knowledge_repository).__name__)"
```

Ожидаемый результат:

```text
PostgresKnowledgeRepository
```

Проверка того, что сервис базы знаний подключён:

```bash
docker compose exec api python -c "from app.container import container; print(type(container.knowledge_service).__name__)"
```

Ожидаемый результат:

```text
KnowledgeService
```

## 5. Проверка таблиц базы знаний

Вход в PostgreSQL:

```bash
docker compose exec postgres psql -U assistant -d assistant_db
```

Команда внутри PostgreSQL:

```sql
\dt
```

Ожидаемый результат:

```text
events
task_dependencies
tasks
```

Эти таблицы соответствуют основным сущностям базы знаний:

- задачи;
- события;
- зависимости между задачами.

## 6. Проверка сохранения задачи

Проверка проводится через frontend:

```text
http://localhost:5173
```

Последовательность действий:

1. Создать новую задачу на сайте.
2. Обновить страницу клавишей F5.
3. Убедиться, что задача осталась в списке.
4. Остановить проект командой:

```bash
docker compose down
```

5. Запустить проект снова:

```bash
docker compose up -d --build
```

6. Открыть сайт и убедиться, что задача сохранилась.

Если задача остаётся после перезапуска Docker, значит она хранится в PostgreSQL, а не только в памяти backend.

## 7. Проверка задачи в PostgreSQL

После создания задачи можно проверить её наличие в базе данных.

Войти в PostgreSQL:

```bash
docker compose exec postgres psql -U assistant -d assistant_db
```

Выполнить SQL-запрос:

```sql
SELECT id, title FROM tasks;
```

Ожидаемый результат: созданная задача должна отображаться в таблице `tasks`.

## 8. Проверка правил базы знаний через API

Правило: событие не может заканчиваться раньше, чем начинается.

Проверочный запрос:

```bash
curl -X POST http://localhost:8000/v1/events \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Некорректное событие",
    "start_at": "2026-05-05T12:00:00Z",
    "end_at": "2026-05-05T10:00:00Z",
    "source": "manual"
  }'
```

Ожидаемый результат:

```json
{
  "detail": "Event end_at must be later than start_at."
}
```

Это означает, что база знаний отклоняет противоречивый факт.

## 9. Автоматические тесты правил базы знаний

Для проверки правил базы знаний используется файл:

```text
apps/api/tests/knowledge/test_rules.py
```

Тесты проверяют:

- корректное событие проходит проверку;
- событие с неправильным временным интервалом отклоняется;
- дублирующиеся зависимости отклоняются;
- задача не может зависеть сама от себя;
- разделяемая задача требует `min_chunk_minutes`;
- `min_chunk_minutes` не может быть больше длительности задачи;
- завершённая задача не считается активной;
- заблокированная задача активна, но не планируется;
- обычная задача активна и может быть запланирована.

## 10. Временный запуск тестов внутри Docker

Если `pytest` не установлен внутри контейнера, его можно временно установить:

```bash
docker compose exec api pip install pytest
```

После этого тесты запускаются командой:

```bash
docker compose exec api python -m pytest tests/knowledge/test_rules.py -v
```

Ожидаемый результат:

```text
9 passed
```

Важно: временная установка пакета действует только внутри текущего контейнера. После пересборки Docker-образа пакет может пропасть.

Это подтверждает, что добавленные правила базы знаний работают корректно и позволяют отклонять некорректные факты предметной области.
